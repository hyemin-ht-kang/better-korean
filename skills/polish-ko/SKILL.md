# polish-ko: 한국어 윤문 검증

한국어 텍스트에서 어색하고 장황한 표현을 찾아 자연스러운 문장으로 고칠 것을 제안한다. 룰 본문은 이 문서에 담지 않으므로, 아래 절차로 룰 파일을 로드해 그 시점의 최신 룰로 검증한다.

## 1. 룰 로드와 병합

아래 순서로 로드해 병합한다. 항목은 합집합으로 합치고, 같은 항목이 충돌하면(예: 기본 룰의 금지어를 프로젝트가 허용) 나중에 로드된 쪽이 이긴다.

1. 플러그인 내장 `default-rules.md` (이 SKILL.md 와 같은 디렉토리): 항상 베이스
2. 개인 `~/.claude/korean-polishing-rules.md`: 있으면 병합
3. 프로젝트 `<repo root>/.claude/korean-polishing-rules.md`: 있으면 병합 (개인 룰보다 우선)

프로젝트·개인 룰 파일에는 예외 선언을 둘 수 있다 (예: "이 프로젝트에서는 `감사`(audit) 허용"). 보고서 머리에 어떤 룰 소스들이 로드됐는지 명시한다.

## 2. 검증 대상 결정

- **인자로 파일 경로가 오면** 그 파일 전체.
- **인자가 없으면** `git diff HEAD`(스테이징 포함)에서 **추가된 텍스트 줄**만. 대상이 없으면 사용자에게 무엇을 검증할지 묻는다.
- **셀프 체크**: 문서·PR 본문·comment 를 작성한 직후라면, 방금 작성한 산출물을 대상으로 같은 절차를 수행한다.

문서 본문, 주석, comment, PR 본문처럼 사람이 문장으로 읽는 한국어 텍스트를 검증하고, 코드 블록 내부와 식별자, URL 은 제외한다.

## 3. 두 패스 검증

### grep 패스 (확정 위반)

`"${CLAUDE_PLUGIN_ROOT}/scripts/grep-pass.sh" <룰 파일...> -- <대상 파일...>` 로 실행하면 코드 블록을 제외한 후보 목록이 나온다. 이 스크립트는 병합된 룰의 「금지어 목록」에서 `금지어 → "대체 표현"` 쌍을 파싱해 대상 텍스트를 검색한다. 위 경로에 스크립트가 없으면 같은 절차(금지어 쌍을 파싱한 뒤 코드 블록을 제외하고 검색)를 직접 수행한다.

- 히트마다 예외 조항(이미 익숙하게 널리 쓰이는 단어, `[미확인]`/`[추정]` 마커, 식별자 안의 부분 문자열)에 해당하는지 확인하고, 해당하면 버린다.
- 남은 건마다 `위치(file:line) / 금지어 / 대체 제안` 을 기록하고, 대체 제안은 룰의 대체 표현을 해당 문장에 맞게 활용한 완성 문장으로 쓴다.

### 판독 패스 (LLM 판단)

병합된 룰의 「패턴 룰」을 기준으로 대상 텍스트를 문단 단위로 판단한다. 은유로 압축한 설계 문장, 명사 나열식 직역투, 정의 없이 등장한 새 용어, "관측"이 문맥에 맞는지, 목록에 없는 압축 조어 신조어, "박다" 계열, 한자 혼용이 판단 대상이다.

- 화살표(→) 요약 표기를 일괄 제외하지 않는다. 표와 코드 블록 안은 제외하되, 문장 안의 화살표는 앞뒤가 명사 체인이면 명사 나열 직역투 후보로 판정한다.
- 건마다 `위치 / 위반 룰 / 근거(왜 위반인지 한 문장) / 수정 제안 문장` 을 기록한다.
- 확신이 낮은 건은 버리지 말고 "판단 필요" 표시로 남긴다 (최종 판정은 작성자의 몫이다).

## 4. 보고

### 대화형 (채팅)

머리에 로드된 룰 소스를 밝히고 `위치 | 층(grep/판독) | 위반 룰 | 수정 제안` 표로 보고한다. 수정 적용은 사용자 확인 후에만 한다.

### CI (PR 리뷰)

개별 코멘트를 낱개로 달지 않고, **인라인 코멘트 전체와 최종 요약을 하나의 리뷰 세션(pull request review)으로 묶어 한 번에 제출**한다 (`gh api repos/{owner}/{repo}/pulls/{n}/reviews` 에 `comments[]` 와 `body` 를 함께 전달, `event: COMMENT`).

- 인라인 코멘트 중 grep 패스 확정 위반은 GitHub suggestion 블록으로 달아 원클릭 적용이 가능하게 한다.
- 인라인 코멘트 중 판독 패스 위반은 근거와 제안 문장을 담아서 단다.
- 리뷰 본문(요약)에는 어떤 룰 위반이 몇 건 발견되어 무엇을 제안했는지 간단히 적고, **작성자의 판단이 필요한 항목**(판독 패스에서 확신이 낮은 건, suggestion 으로 확정하지 못한 건)은 별도 목록으로 명시한다.
- CI 를 실패시키지 않도록 항상 exit 0 으로 끝낸다.

## 5. 룰을 계속 추가하는 피드백 루프

룰 파일은 `.claude/` 하위에 있어 눈에 덜 띄고 갱신을 잊기 쉬운데, 룰 리스트를 계속 늘려 가는 것이 이 플러그인 운영의 핵심이므로 스킬이 그 일을 챙긴다.

- **세션 중 사용자가 표현을 정정하면**(예: "이 단어 어색해", "이렇게 바꿔줘") 이 스킬의 검증 결과에 대한 반응이든 일반 대화 중이든 "이 항목을 윤문 룰 리스트에 추가할까요?"라고 묻는다.
- 추가처는 두 갈래로 제안한다. **프로젝트 룰**(`.claude/korean-polishing-rules.md`, 팀과 공유)이나 **개인 룰**(`~/.claude/korean-polishing-rules.md`, 모든 프로젝트에서 사용) 중 하나이고, 파일이 없으면 만들면서 형식(default-rules.md 와 같은 구조)을 갖춘다.
- 추가할 항목은 grep 으로 검색되는 `금지어 → "대체 표현"` 형식이 우선이고, 패턴으로 반복될 정정이면 「패턴 룰」에 문장으로 추가한다.
